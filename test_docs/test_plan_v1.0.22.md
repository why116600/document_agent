## 1. 测试目标与依据

项目的目标是根据自然语言需求和组织自建资料，新建或修改 Word，并可将资料录入篇章摘要树和实体关系知识图谱，供后续检索使用。本轮重点回答三个问题：

1. 能否正确识别任务和目标文件，准确完成新建、全文替换、局部修改、整体润色、仅格式调整及组合任务？
2. 能否保护原稿和未要求修改的内容，并在输入、模型、检索或保存失败时给出可判断的结果？
3. 两类知识存储能否分别写入和查询，其检索内容能否进入实际写作流程，且事实能追溯到合成来源？

依据按以下顺序使用：负责人确认的需求与验收口径、锁定版本中的 README、对应源代码、针对该版本的执行证据。README 是需求线索；实现代码用于定位测试入口和风险，不将“代码这样做”自动当成“业务应该这样做”。需求与实现冲突时先列待确认项。

## 3. 测试思路：先保数据，再验证功能，再核验知识帮助

### 3.1 按风险安排顺序

| 顺序 | 风险 | 优先覆盖 |
| --- | --- | --- |
| 第一层 | 改错文件、覆盖原稿、失败却报告成功、保存半成品 | 目标歧义、原稿哈希、异常退出、另存/覆盖、组合任务失败 |
| 第二层 | 改错范围、漏替换、数字被改写、格式任务修改文字 | patch 范围、跨 Run 替换、表格、事实清单、逐元素文字对比 |
| 第三层 | 文件能打开但图片、关系、公式、页眉页脚或版式受损 | DOCX 包和关系检查，加实际 Word 打开及视觉检查 |
| 第四层 | 资料读错、检索不命中、树和图谱混淆、编造来源 | 解析对照、两类存储独立测试、带来源的问答和集成写作 |
| 第五层 | 模型或环境切换后结果不可复现 | 固定样例、提示词和模型矩阵，保留失败及重试证据 |

### 3.2 三层检查相互补充

1. **规则和协议检查**：离线验证目标匹配、词对替换、步骤排序、状态和异常分支；模拟仅用于精确触发分支，并标记“离线”，不能代替真实模型及文件保存验收。
2. **真实流程检查**：在已确认的被测基线上，经锁定版本入口处理合成样例，保留需求原文、脱敏日志、退出码、实际输出路径和模型信息。
3. **结果检查**：程序化比较文字、数字、表格及 DOCX 结构，再实际打开 Word 检查。文本一致、ZIP 可读取或退出码为 0 都不能单独证明格式保真或任务成功。

纯格式任务以文字和结构保护为硬条件；生成式润色允许措辞变化，但指定事实、数字、否定关系和章节边界不能被随意改动。写作质量采用事先列明的检查表，不以“看起来还行”作唯一结论。

### 3.3 模型与运行方式矩阵

| 维度 | 首轮安排 | 记录方式 |
| --- | --- | --- |
| README 默认模型 DeepSeek | 按负责人确认的版本、公开启动入口及授权配置执行 | 记录实际提交、必要配置标识、请求与实际模型、超时/重试、最终状态；配置未就绪时保留未执行或实际尝试后的阻塞 |

测试对象与模型配置由负责人确认，不为执行计划擅自切换代码或模型。执行实例建议编码为 `TC-xx/子例/模型/序号`，例如 `TC-15/A/DeepSeek/01`。主用例状态由其已纳入范围的子例汇总；仍有必要子例未执行时，不能把整个主用例标为通过。

### 4.3 通用结果核对

每次运行至少保留：基线标识、样例版本及 SHA-256、需求原文、候选文件列表、期望目标/模式、请求与实际模型、启动方式、运行时间、退出码、输出实际路径、结果摘要及证据位置。路径在公开材料中使用仓库相对位置或脱敏标识。

所有另存场景执行前后计算输入 SHA-256；“原稿未变”必须有前后哈希支持。哈希只用于保护原稿，不能用来判断润色输出是否正确。对输出依次做：有效 DOCX/可打开检查、文字和事实对照、结构和关系检查、人工视觉核验。复杂格式基于源稿逐项核对，不能凭脚本文字长度校验宣布通过。

知识测试使用独立的可清理测试数据范围，记录录入前后节点、关系和来源计数；清理只针对本轮明确归属的数据。不得在共享数据上使用全库清空或无过滤删除。

| 07 分别验证两类知识存储 | 先测篇章摘要树，再测实体关系图谱、查询及降级 | TC-30～TC-34 | 两类存储各自的写入/查询/来源与标准题结果 | 两类功能各有独立结论，不能互相替代 |
| 08 验证知识库完整流程 | 录入虚构资料，不传原文件进行检索写作；补充代表模型子例 | TC-35～TC-36及已选代表子例 | 实际录入范围、检索来源、模型路由、最终 Word | 能核对用了什么资料、是否串源、无答案是否编造 |
| 09 汇总首轮并移交 | 汇总覆盖、通过/失败/阻塞/未执行，形成具体问题队列 | 汇总步骤，不新增 TC 编号 | 首轮报告、当前缺陷表、证据摘要与未覆盖范围 | 每个纳入范围的实例都有真实状态；不要求全部通过才报告 |
| 10 对修复版本回归 | 使用原失败样例与原需求复测，再覆盖受影响的相邻功能 | 关联原用例与缺陷 | 修复版本、原样例回归结果、关闭或重开理由 | 满足关闭标准才关闭；未修复与未验证的问题保留 |

每个子例都按同一套动作执行：**准备输入 → 写下预期 → 运行一个任务 → 对照成果 → 登记结果**。一次只推进当前子例，完成后再进入下一项。

TC-30～TC-34 的直接类调用、索引条件控制，以及 TC-25/TC-28/TC-29 的故障注入，需要测试人员另行准备隔离驱动。本文提供完整测试设计，不表示已有一键自动执行器或已制作全部实体样例。按第 4 节展开并登记子例后再执行，不把一个子例成功当成整条主用例通过。

## 7. 进度、缺陷与退出标准

### 7.1 进度口径

主用例统计总数为 36，子例另列。状态必须满足“通过＋失败＋阻塞＋执行中＋未执行＝当前纳入范围数”，并标明统计对象为主用例还是子例，不能混算。若正式范围调整，保留调整前范围、理由和批准记录。

“通过”必须有预期和证据；“失败”表示实际表现与已确认预期不符；“阻塞”要有具体前置条件和责任/处理方向；“未执行”是尚未尝试，不伪装成阻塞。需求不清晰的项目先列待确认；不能因没执行就填缺陷，也不能以“模型随机”删除真实失败记录。

每个确认问题按[缺陷登记表](defect_register_v1.0.22.md)记录基线、输入、指令、最小复现、预期/实际及证据；没有明确预期、锁定版本与实际复现时，不直接登记确认 DEF。静态疑点和需求待确认项独立记录。问题归属实际被测版本，不能跨版本混计。Issue 编号和标签只有在实际创建或经负责人核实后填写。

### 7.2 首轮完成与发布准入是两件事

首轮测试可以在存在失败和阻塞时完成移交，条件是：

- 约定范围的每个主用例及子例均有真实状态，所有未执行/阻塞项说明原因和后续安排；不以“全部通过”作为编写首轮报告的前提。
- 失败有足够复现证据并已去重；原稿保护、目标错误、假成功等高风险问题单列，不被平均通过率掩盖。
- 结论指向实际基线、模型和样例，不把其他版本或配置的结果归入本批次，不把小样例结果扩大成复杂业务保证。
- 资料已脱敏，提交内容由人工审阅；凭据、运行目录、原始日志、数据库与模型文件不进入默认提交范围。

是否允许交付用户使用或发布，由负责人根据已确认的阻断缺陷、未覆盖风险和业务标准决定。本计划不代替发布审批，不编造“已验收”或“已同意上线”。
