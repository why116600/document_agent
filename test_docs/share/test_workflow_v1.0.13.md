# document_agent 单项测试执行与交付流程 v1.0.13

文档版本：v1.0.13。适用范围：测试设计、实际执行、材料归档、结果摘要和移交。当前两项探索是示例材料，不因本流程落地而重新执行或变成正式用例通过。

**固定做法：一次选择一个明确用例，先固定输入和预期，执行后保留真实成果；先形成详细核对，再用 README 展示结果与建议，最后检查共享范围并按授权提交。**

## 1. 每项按八步完成

| 步骤 | 实际动作 | 本步留下什么 | 完成条件 |
| --- | --- | --- | --- |
| 01 选定对象 | 选择用例/子例，明确正式测试或探索，记录实际版本、入口和变更范围 | 用例编号、测试类型、基线记录 | 不混用原项目和本地扩展结果，不自动换代码 |
| 02 冻结输入 | 准备合成资料，分开原件、运行副本和输出；运行前计算哈希 | inputs 原件副本、清单和运行前标识 | 能识别原件并在执行后核对，私人材料不进入共享包 |
| 03 先定预期 | 写清内容、范围、保留对象、字数口径、字体颜色、另存/覆盖等 | expected 检查清单 | 含糊项标待确认；如果先做探索，也不能事后补造“运行前已冻结” |
| 04 执行任务 | 使用已授权入口，保存准确需求、实际路由、尝试和退出状态；失败也保留 | outputs 实际成果及本地原始证据 | 未改产品或更换输入来掩盖失败，未知值不编造 |
| 05 对照检查 | 对比事实、数字、作用域、原稿哈希、对象结构和文字格式；需要时实际打开核查页面 | reports 逐项对照和检查数据 | 结构检查与页面核查分别记录，文件存在不算全部通过 |
| 06 判定归属 | 区分符合、失败、待确认、未验证和阻塞；确认问题给最小复现 | 逐项结论、观察或缺陷及后续动作 | 明确预期、基线和真实复现齐备才登记确认缺陷，适配与原项目分开 |
| 07 更新入口 | 从报告提取结果、观察和建议；补齐材料链接 | README 结果摘要 | 数字能追溯，建议标是否执行，不能把部分符合写成全部通过 |
| 08 检查与移交 | 运行只读交付检查，人工核对证据与隐私，再逐文件选取提交范围 | 检查结果、交接和精确清单 | 静态检查与人工核对分别完成；Git 操作按用户明确授权执行 |

完整执行清单见[单项清单模板](templates/run_checklist_v1.0.13.md)。执行人、责任人、Issue 和审核人未知时据实标记，不补造人选和记录。

## 2. 材料固定分五类

每个材料包保留 `cases/`、`inputs/`、`expected/`、`outputs/`、`reports/` 和包 README、manifest。按稳定用例号关联同一任务，输入/成果保留自身真实文件名与版本。

当前示例是[两项探索材料包](exploration_v1.0.11/README.md)。其中预期与哈希为事后整理，缺少运行时证据的限制仍然保留，不能用新流程倒填。以后新任务尽量在运行前完成步骤 01～03。

当前 manifest 记录输入和实际成果，不要求它登记所有说明文档。至少包含 `package_version`、`cases`、`artifacts`；每份归档材料记录 `case_id`、`role`、包内相对 `path`、`bytes`、`sha256`。角色为 `input` 或 `actual_output`，每个用例至少各一份。路径不写个人绝对目录。

机器复核文件置于 reports，文件名采用 `file_checks_v版本.json`，其中的逐例记录含 `case_id`。它记录检查事实；不能单凭某个布尔值生成业务通过结论。未支持的新结构先人工核对或独立扩充检查器，不静默当通过。

## 3. README 固定用四块内容

| 顺序 | 必须让读者看见 | 判断标准 |
| --- | --- | --- |
| 1 结论摘要 | 已实际执行多少、当前确认到什么、还有什么待确认 | 探索与正式用例分开，数字来自报告，不虚构覆盖和通过率 |
| 2 测试结果 | 用例、主要实际结果、当前判断、直接打开成果的链接 | 明确“已观察到完成”“当前核对符合”与“整体通过”的差别 |
| 3 观察与建议 | 现象、影响或未知影响、具体下一步、是否已执行 | 不把建议写成已完成，不把待确认观察直接编号为确认缺陷 |
| 4 详细证据 | 用例、输入、预期、成果、报告和归档清单 | 链接有效，读者能从结论追到实际材料 |

入口的摘要与报告矛盾时先修正文档归属，不修改真实成果来迎合摘要。建议优先写成可执行动作，如“明确字数口径后复测”“并排核对页眉页脚与分页”，不止写“建议优化”。

## 4. 只读交付检查

从仓库根目录执行：

```powershell
python -B test_docs/share/tools/check_test_delivery_v1.0.13.py --package test_docs/share/exploration_v1.0.11
```

脚本只读指定材料，检查目录、清单、用例关联、字节/哈希和链接，并筛查有限的敏感文本模式。它不调用产品、模型或数据库，不读取环境凭据，不补文件、不改 Word，不安装依赖、不操作 Git。

退出码 0 表示当前静态交付检查通过；1 表示存在需处理的交付问题；2 表示参数用法有误。结果不是功能验收、页面检查、完整安全审计或发布批准。原始凭据/请求/日志、DOCX 元数据和页面效果仍需按范围人工审查。

输出中的 `manual_review_required` 始终提醒人工复核；`manual_review_notes` 非空时，先处理注明的报告结构或证据核对事项，不因退出 0 跳过。检查器始终标明 `business_validation=not_performed`。

入口说明、材料包、输入/成果各自保留真实版本，不能机械要求全部同版。检查器不会把当前归档哈希当运行前证据，不会把现有两个观察升级缺陷，也不会把两项探索算进正式 36 条用例。

## 5. 谁做什么，何时交接

测试人员实际执行并核对预期；Agent 协助准备资料、检查和归纳，但不替人补造已执行事实。需求口径由相应负责人或用户确认；缺陷修复由另获授权的开发任务处理，按原失败样例回归后再关闭。

每次交付前检查：材料可定位、结果有依据、建议可执行、隐私已审查、版本自洽、共享文件清单明确。达到的是“本次测试记录可审阅”，不能把它等同为产品已无缺陷。

修改范围与当前候选见[工作流交接](workflow_handover_v1.0.13.md)。原[测试计划](test_plan_v1.0.9.md)、[控制规则](test_control_v1.0.9.md)和[缺陷队列](defect_register_v1.0.9.md)继续适用；本流程只把材料交付和入口表达落实为固定操作。
